# 0002: Tenant isolation with a pooled schema, row-level security and typed tenant context

- Status: proposed
- Date: 2026-11-02
- Risk tier: 1 (tenant isolation)

## Context

Tetsu serves many tenants (for fitness, one tenant is one studio brand) from one
binary and one Postgres cluster (ADR-0001). The market scan targets thousands of
small studios, most with modest data, so per-tenant infrastructure cost matters.
A single cross-tenant read (one studio seeing another's members or payments) is
the worst failure the platform can have.

ADR-0001 already fixes two constraints that shape this decision: each module owns
its own Postgres schema, and every operation on tenant data takes a
`TenantContext` from `tetsu-tenancy`. What is not yet decided is how tenant data is
laid out, how the database enforces isolation, and how tenant IDs are generated.

Facts that matter (PostgreSQL documentation):

- Superusers, roles with `BYPASSRLS`, and table owners bypass row-level security
  unless the table has `FORCE ROW LEVEL SECURITY`.
- With RLS enabled and no matching policy, access is default-deny.
- Primary key, unique and foreign key checks always bypass RLS, so constraints can
  leak or link rows across tenants unless they include the tenant ID.
- PostgreSQL 18 ships a built-in `uuidv7()` function (RFC 9562, time-ordered).

## Decision

Use the **pool model**: all tenants share the same tables, every tenant-owned row
carries a `tenant_id`, and isolation is enforced **twice**: by the Rust type system
(`TenantContext`) and by **Postgres row-level security**. Tenant IDs are
**UUIDv7, generated by Postgres 18's built-in `uuidv7()`**.

### Data layout

- Every table holding tenant data has `tenant_id uuid NOT NULL`. Control-plane
  tables that are genuinely global (the tenant registry itself, platform
  configuration) are the only exceptions, and each one is listed in its module's
  migrations with a comment saying why.
- Every primary key, unique constraint and index on tenant data leads with
  `tenant_id`: `PRIMARY KEY (tenant_id, id)`, `UNIQUE (tenant_id, email)`.
  Uniqueness is per tenant, so a constraint violation never reveals that a value
  exists in another tenant.
- Every foreign key between tenant tables includes `tenant_id`:
  `FOREIGN KEY (tenant_id, class_id) REFERENCES scheduling.classes (tenant_id, id)`.
  Because FK checks bypass RLS, this is what stops a row in tenant A from
  referencing a row in tenant B.

### Database enforcement

- Every tenant table gets `ENABLE ROW LEVEL SECURITY` **and**
  `FORCE ROW LEVEL SECURITY`, plus one policy for all commands:

  ```sql
  CREATE POLICY tenant_isolation ON booking.bookings
    USING (tenant_id = NULLIF(current_setting('tetsu.tenant_id', true), '')::uuid)
    WITH CHECK (tenant_id = NULLIF(current_setting('tetsu.tenant_id', true), '')::uuid);
  ```

  If no tenant is set, the expression is `NULL` and no rows match: fail closed.
  `NULLIF` covers the empty string a custom setting reverts to after a
  transaction-local value ends.
- **Roles.** `tetsu_owner` owns the schemas and runs migrations; it cannot log in
  from the running service. `tetsu_app` is the only role the service connects as:
  `NOSUPERUSER NOBYPASSRLS`, not an owner, granted only the DML it needs.
  `FORCE` is kept anyway so an ownership mistake does not silently switch
  isolation off.
- **Setting the tenant.** The tenant is set per transaction, never per
  connection: `SELECT set_config('tetsu.tenant_id', $1, true)` as the first
  statement. Transaction-local settings end with the transaction, so a pooled
  connection cannot carry one tenant's context into the next request.

### Type-level enforcement

- Ports that touch tenant data take `&TenantContext`. Domain code never resolves
  or switches tenants.
- The Postgres adapter exposes one way to get a transaction on tenant data: a
  `begin_tenant(&TenantContext)` call that opens the transaction and sets
  `tetsu.tenant_id` before returning it. Repository code receives that
  transaction type, never a raw pool. (The exact type lands with the first
  Postgres adapter crate.)
- Domain events and outbox rows carry `tenant_id`. A consumer builds its
  `TenantContext` from the event and opens its own tenant transaction.
- Work that spans tenants (billing runs, reminders) iterates the tenant registry
  and opens one tenant transaction per tenant. Nothing in the running service
  reads across tenants in one query.

### Tenant IDs

- `tenancy.tenants.id uuid PRIMARY KEY DEFAULT uuidv7()`. Postgres 18 is the
  minimum supported version.
- `TenantId` in Rust stays a `u128` carrier that formats and parses UUIDs. The
  `uuid` crate is not added now; it is adopted only if Tetsu needs to mint IDs
  before insert (for example offline bulk import), and then it must generate
  version 7 to stay consistent.
- A tenant ID is an identifier, not a secret. Nothing may treat knowing one as
  permission; authorization always goes through identity and access.

## Options considered

### Isolation model

1. **Pool with RLS and typed context (chosen).** Cheapest per tenant, one set of
   migrations, works with one schema per module. A missed filter in Rust is caught
   by RLS and vice versa. Costs: noisy-neighbor risk on shared tables, and every
   table must follow the rules above, which needs tooling to check.
2. **Pool with application filtering only.** Same layout without RLS. One missing
   `WHERE tenant_id = ...` leaks data, with nothing behind it. Rejected for a
   tier-1 concern.
3. **Schema per tenant (bridge).** Conflicts with ADR-0001's schema per module:
   it would mean modules × tenants schemas, migrations run once per tenant, and
   catalog bloat at thousands of studios.
4. **Database per tenant (silo).** Strongest isolation and easy per-tenant
   restore, but cost and operational load far beyond what small studios pay for.
   Kept open as a possible premium tier: the same code runs against a dedicated
   database because isolation never depends on which database a tenant lives in.

### Tenant ID generation

1. **UUIDv4 from `gen_random_uuid()` (current code comment).** Random, reveals
   nothing, but scatters inserts across B-tree indexes; every key that leads with
   `tenant_id` inherits that.
2. **UUIDv7 from Postgres 18 `uuidv7()` (chosen).** Time-ordered, so index
   locality is good, and no new dependency. Reveals the tenant's creation time,
   which is not sensitive. Monotonic within one session only, which is enough for
   a registry with few inserts.
3. **UUIDv7 from the `uuid` crate in Rust.** Lets the application mint IDs before
   insert, but adds a dependency for no current need and splits ID generation
   between two places.

## Consequences

- Postgres 18 is a hard requirement for every deployment.
- Every module's migrations must follow the layout and policy rules. To make that
  checkable, a test helper (with the first Postgres adapter) queries
  `pg_class.relrowsecurity`, `pg_class.relforcerowsecurity` and `pg_policies` and
  fails if any table with a `tenant_id` column lacks forced RLS and the tenant
  policy, or if any unique or foreign key on it omits `tenant_id`.
- Tier-1 tests: adversarial module tests per module (tenant A cannot select,
  insert, update or delete tenant B's rows; no tenant set returns zero rows; a
  cross-tenant FK insert fails) and property tests interleaving operations for
  several tenants. Changes to these rules or the policy need two-step review.
- `TenantContext::new` is public today. When identity and access lands, its
  construction should be limited to inbound adapters after authorization; that is
  a follow-up, tracked with the identity ADR.
- Support or operator access across tenants is not part of the running service.
  If it is needed, it gets its own audited role and ADR.
- Large tenants can hurt neighbors on shared tables. Watch per-tenant query load;
  the silo option above is the escape hatch.
