# Operator enrollment and admin controls: a practice review

Research on 2026-11-15 for [#110](https://github.com/heavymedl-labs/tetsu/issues/110), step 3 (commit `0ed6f47`):
the operator command's invite links, disabling operators, ending sessions, and the audit events each records.
Its step 3 findings are fixed in the commit that adds this page; its step 4 findings feed the page that consumes
the invite link.

## Summary

Step 3 (commit 0ed6f47) mostly follows current practice, but it has one high-severity correctness defect that must be fixed before anything builds on it. **`disable_operator` can return true, record `identity.operator_disabled`, and still leave a live session or invite link** when a login or `invite` holding the operator row commits while the disable waits. Two independent reviews reproduced this on PostgreSQL 18.7. The cause is that every sub-statement of a data-modifying CTE shares the snapshot taken before the lock wait. The surviving session lasts up to 15 minutes idle or 8 hours absolute, because `use_session` never checks `disabled_at`. That breaks ASVS 5.0 7.4.2 and the commit's own claim that "a disable at the same moment ends what it started". The token design itself is strong. It uses 256 bits from a CSPRNG, is stored as SHA-256, lasts one hour, allows one open link per operator, and keeps the token in a URL fragment. It sits at the strict end of what Teleport and Microsoft Entra do. The other step 3 gaps are an audit payload with no actor or outcome, a test that fails about 1.4% of the time, an overloaded SQLSTATE, and no re-enable command. The largest risks left for step 4 are binding a passkey to an operator that already has one, and consuming the token before registration finishes.

## One shared snapshot lets a disabled operator keep logging in

`disable_operator` is a single statement. Its UPDATE CTE sets `disabled_at`, and two more CTEs delete the operator's sessions and enrollment row through `USING disabled`. The RETURNING join is the documented way to pass rows between sub-statements. But PostgreSQL states that **all sub-statements "are executed with the same snapshot ..., so they cannot 'see' one another's effects on the target tables"** ([PG 18, WITH queries](https://www.postgresql.org/docs/18/queries-with.html)). In READ COMMITTED, a blocked UPDATE re-checks only the rows its snapshot already found. It "does not see effects of those commands on other rows in the database" ([PG 18, transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html)). So when `start_session` holds the operator row `FOR SHARE` and has inserted a session, the disable blocks on the UPDATE. It then sets `disabled_at` after the login commits, and its DELETE CTEs, still on the old snapshot, never see the new session. The reproduction printed `as committed (CTE disable_operator) → t; sessions left=1 links left=1 disabled=true`. `issue_invite` takes the same `FOR SHARE` lock, so it hits the same defect, and a link can survive for an hour on a disabled account.

The opposite order is sound. When the disable commits first, `start_session` raises "no enabled operator" and `issue_invite` returns false. **`FOR SHARE` is the right lock**, because setting a non-key column takes `FOR NO KEY UPDATE`, which conflicts with `FOR SHARE` but not with `FOR KEY SHARE` ([PG 18, explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html)). Neither review found a new deadlock cycle. The fault is in the comment in `0002_operator_controls.sql` and in the Identity README, which both say the disable "waits for it and then ends the session it started". It does not.

The fix has three parts, and step 3 needs all three. First, rewrite `disable_operator` in PL/pgSQL as separate statements: `UPDATE ... WHERE disabled_at IS NULL; IF NOT FOUND THEN RETURN false; END IF;`, then `DELETE FROM sessions`, then `DELETE FROM invites`, then `RETURN true`. **"VOLATILE functions obtain a fresh snapshot at the start of each query they execute"** ([PG 18, function volatility](https://www.postgresql.org/docs/18/xfunc-volatility.html)), so the DELETEs start after the lock wait and see the committed session. The same reproduction left 0 sessions and 0 links. `CREATE OR REPLACE` can change the language while keeping the boolean return type, and ownership and grants carry over ([PG 18, CREATE FUNCTION](https://www.postgresql.org/docs/18/sql-createfunction.html)). Second, as defense in depth, make `use_session` join `operators` on `disabled_at IS NULL`. Then any row that leaks through this race, or a future one, dies at its next request, at the cost of one primary-key lookup. Third, replace `a_disable_racing_logins_leaves_no_session`. It spawns six logins with no forced order and passes while the bug exists. The new test opens a transaction on its own connection and calls `start_session`, and a second variant calls `issue_invite` instead. It then starts the disable and waits until `pg_stat_activity` shows it with `wait_event_type = 'Lock'`. Finally it commits the first transaction and asserts that no sessions and no links remain.

Two neighbouring races are acceptable, but they should be documented. A request whose `use_session` committed just before the disable finishes that one request. Closing that window fully is an ASVS L3 matter (8.3.2, "applied immediately") ([ASVS 5.0 V8](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0_release/5.0/en/0x17-V8-Authorization.md)). `end_operator_sessions` and `end_realm_sessions` take no operator lock, so a login that commits during them survives. That is fair as "ends what exists now", but an incident responder reading "end everything" would expect more. Either say so in the help text, or for one operator lock the row `FOR NO KEY UPDATE` and then delete in a separate statement, as above.

## The audit events name what happened but not who did it

The event set is the right one. Creation, credential issuance, disabling, and ending sessions match ASVS 16.3.3's documented security events, NIST AC-2(4)'s "creation, modification, enabling, disabling, and removal" ([csf.tools AC-2](https://csf.tools/reference/nist-sp-800-53/r5/ac/ac-2/)), and OWASP's "always log" list for user management and administrative actions ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). The transactional outbox makes the record stronger than many products, where audit writes are best effort. The payloads fall short, though. They hold only `{"operator_id"}`, `{"operator_id", "realm", "ended"}`, or `{"realm", "ended"}`. **ASVS 5.0 16.2.1 (L2) requires "when, where, who, what"** ([ASVS 5.0 V16](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0_release/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md)). NIST AU-3 requires the outcome and the "identity of any individuals ... associated with the event" ([csf.tools AU-3](https://csf.tools/reference/nist-sp-800-53/r5/au/au-3/)). Kubernetes and GitLab audit records both carry an actor, a source address, and a result status ([Kubernetes audit API](https://kubernetes.io/docs/reference/config-api/apiserver-audit.v1/), [GitLab audit events](https://docs.gitlab.com/administration/compliance/audit_event_reports/)).

The database login is shared, so the CLI can only record an actor the machine claims about itself: the OS user, the hostname, the command and its arguments without tokens, the Tetsu version, and `source: "cli"`. Label it `asserted: true`. This mirrors Teleport, which separates the authenticated `user` from the OS `login`, and Kubernetes, whose docs say `userAgent` "must not be trusted". Setting `application_name` to the same actor puts it in the Postgres logs as well. A bound actor needs per-operator database logins or admin pages behind the `/ops` session. The `source` marker matters for another reason. Whoever holds the database credential can mint an operator with `tetsu operator create`, which makes it the most privileged path in the system and in effect its break-glass account. Entra's guidance is to "monitor all sign-in and audit log activity for emergency access accounts with alerts" ([Microsoft Learn, emergency access accounts](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/security-emergency-access)), so these events should eventually feed an alert, not just storage.

Outcomes are inconsistent too. `disable_operator` and `issue_invite` use `.then_some(...)`, so a disable of an unknown or already disabled ID records nothing, and so does a refused enroll. Meanwhile `end-sessions` records `ended: 0`. Follow AU-3(e) and OWASP's "Result status" with one rule: **every command that reaches the database records one event with `outcome` set to `changed`, `no_change`, or `refused`**. A typo'd or probing disable then leaves a trace. Failures that roll back cannot land in the outbox, so they go to stderr and the structured log. An optional `--reason` on disable, enable, and end-sessions is cheap and follows OWASP's "Reason" attribute and Teleport's lock `--message` ([Teleport locking](https://goteleport.com/docs/identity-governance/locking/)). Length-limit it and encode it. While touching payloads, stop building JSON with `format!`. It is safe today, since only integers and the fixed realm name are interpolated, but an actor or reason string would make it injectable. Use `jsonb_build_object` with typed parameters, and compare payloads in tests as `jsonb` rather than text, so the tests stop depending on jsonb's key ordering.

A destination question stays open beyond step 3. ADR-0045 has the audit consumer store events "per tenant", but operator events go to `outbox_global`, and delivered rows are deleted after 7 days. ASVS 16.4.2 and 16.4.3 want logs that cannot be modified and that reach a logically separate system. That needs an ADR decision before the dispatcher exists, not a code change now.

## Four smaller step 3 defects, all cheap to fix

**`issue_invite` reads `clock_timestamp()` twice**, and that clock "changes even within a single SQL statement". So `ends_at - issued_at` sometimes falls a few microseconds short of one hour. In 200,000 evaluations on the 18.7 server, about 1.4% were not exactly one hour. That means `an_invite_link_is_stored_hashed_for_an_hour_and_replaced` fails on roughly 1 to 2% of runs. Read the clock once, as `start_session` and `use_session` already do.

**The adapter maps any `NO_DATA_FOUND` (P0002) from any statement to `Error::Invalid`**, and passes the database message to the caller. Today only `start_session` raises it. But PL/pgSQL raises the same code for every `SELECT INTO STRICT` that finds no rows ([PG 18, PL/pgSQL statements](https://www.postgresql.org/docs/18/plpgsql-statements.html)), so a later storage bug would surface as "invalid input". Either give `start_session` a project-specific SQLSTATE ("any error code consisting of five digits and/or upper-case ASCII letters, other than 00000", not ending in 000 ([PG 18, errors and messages](https://www.postgresql.org/docs/18/plpgsql-errors-and-messages.html))) or make it return a boolean like `issue_invite`. The second option also makes the contracts consistent.

**There is no way back from disable.** NIST AC-2(f) lists "create, enable, modify, disable, and remove", and every product reviewed has a reverse path. Okta has unsuspend and reactivate, and Teleport removes a lock ([Okta, deactivate and delete](https://help.okta.com/oie/en-us/content/Topics/users-groups-profiles/usgp-deactivate-user-account.htm)). Keeping the row rather than deleting it is right, since Okta also requires deactivation before deletion. An `operator enable <id>` should clear `disabled_at`, record an event, and never restore sessions or links. Whether passkeys survive a disable can wait until passkeys exist. Okta keeps factors on deactivation. A stricter rule, deleting them and requiring a new link, suits a tiny operator set. If enable is out of scope for step 3, record that in the ADR now.

**The rest are low.** Two overlapping `invite` calls both succeed, and the second token wins, which is correct under "a new link replaces the last". But the first printed link silently dies, so add a test that pins this, and consider `replaced: true` in the event. `create` commits the operator and then enrolls in a second transaction, so a failed enroll should report the new ID, letting the maintainer run `invite <id>`. The `IsTerminal` check is a guard against accidents, not a boundary, because `script(1)` writes "everything on your terminal session" to a file ([man7, script(1)](https://man7.org/linux/man-pages/man1/script.1.html)). Teleport prints its one-hour invite with no such check ([Teleport, local users](https://goteleport.com/docs/zero-trust-access/rbac-get-started/users/)). Reword ADR-0040's "prints the link only to the terminal that ran it" as "refuses non-terminal output, so a link never lands in a log or pipe by accident", and name database access as the real trust boundary. A guard or `--force` before disabling the last enabled operator is optional, since `create` is the recovery path. Finally, `query_recording`'s atomics are correct with `Relaxed`, but they exist only because the closure is `Fn + Sync`. Reading the returned rows after the call removes them.

## Step 4 must not consume the link until the passkey exists

The token passes every quantitative rule found. It beats NIST's 112-bit binding code and ASVS's 64-bit floor, it is single use, it expires in an hour, and it is hashed at rest ([NIST SP 800-63B-4, authenticator events](https://pages.nist.gov/800-63-4/sp800-63b/events/), [ASVS 5.0 V6](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x15-V6-Authentication.md)). The one-hour life and the one-link replace rule match Entra's Temporary Access Pass, whose default lifetime is one hour and where "each user can only have one TAP" ([Microsoft Learn, TAP](https://learn.microsoft.com/en-us/entra/identity/authentication/howto-authentication-temporary-access-pass)). The link origin comes from `TETSU_ORIGIN`, never the Host header, as OWASP requires. The fragment never reaches the server or the `Referer` header ([MDN, Referer](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referer)). What remains is how the page consumes the link.

**The most important rule is "only for an account with no credential", and step 3 cannot enforce it yet** because no passkey table exists. Once passkeys exist, `invite` on an enrolled operator would mint a link that adds a passkey to a privileged account without a fresh login. ASVS 6.4.1 forbids that kind of rebind, and NIST 4.1.2.1 says it needs authentication at the account's level, plus a notification. Step 4 must refuse in `issue_invite` and again in the finish transaction, under the same `FOR SHARE` pattern as `start_session`, so two tabs cannot bind two passkeys. The finish transaction must also refuse a disabled operator. Rank 1 shows why: a lock alone does not guarantee the disable deleted the link.

**Consume the token at finish, never at begin or on GET.** In January 2025, Microsoft's mail scanners were seen running page JavaScript and sending its POSTs, which burned single-use login links ([Bert Hubert](https://berthub.eu/articles/posts/shifting-cyber-norms-microsoft-post/)). Supabase users report the same ([Supabase discussion #41618](https://github.com/orgs/supabase/discussions/41618)). Tetsu's link is printed, not emailed, but it may be pasted into chat to reach another device. A scanner cannot produce a WebAuthn credential with user presence, so it can only do harm if a request that comes before finishing has side effects. The safe shape has four steps. `GET /ops/join` serves a static page with `Cache-Control: no-store` and `Referrer-Policy: no-referrer` ([OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)). The script reads `location.hash` and calls `history.replaceState` at once to drop it. A button starts registration with a begin POST, which checks the token and stores a challenge that expires within minutes, without consuming the token. The finish POST verifies the attestation and, in one transaction, runs `DELETE ... WHERE token_hash = $1 AND ends_at > now() RETURNING operator_id`, rechecks the operator, and inserts the passkey. Both POSTs take ADR-0059's Origin and `Sec-Fetch-Site` checks and the login rate limits, and every invalid case gets one generic error.

**The rest of step 4 finishes the lifecycle record.** NIST requires the "date and time of significant authenticator life cycle events" and recommends the binding's source ([NIST 800-63B-4 events](https://pages.nist.gov/800-63-4/sp800-63b/events/)). So add `invite_redeemed` with time, IP, user agent, credential ID, AAGUID, and the user-verified flag, plus `join_refused` with a reason class but never the token. Use the actor and outcome fields from rank 2. Show "passkeys: N, open link until" in `operator list`. With one operator and no mail adapter, that list and the audit record are the notification. Do not log the operator in after enrollment. OWASP says "don't automatically log the user in", and NIST says the CSP "SHOULD encourage the subscriber to authenticate with the new authenticator". Teleport does the opposite, so this is a judgment call, but a login proves the passkey works. Set `userVerification` and `residentKey` to `required`. Confirm that `TETSU_ORIGIN` is the operator host, since a passkey made under the wrong RP ID fails in the operator realm. Store the AAGUID now so a later attestation gate has data. Sweeping expired rows is optional, because the `ends_at` check already treats them as dead and each operator holds at most one.

## Conclusion

The step 3 bug says more about method than about this one function. The design reasoning was right: it chose the correct lock mode, closed the opposite race, and wrote a concurrency test. Every check still passed, because one PostgreSQL rule (a CTE keeps its snapshot across a lock wait) undid the reasoning, and only a forced interleaving shows it. Two habits follow for steps 4 and later. Every Tier 1 race test should pin its interleaving through `pg_stat_activity` rather than hope for it. And `disabled_at` should be checked wherever a credential is used (`use_session`, link redemption, later passkey login), not only cleaned up at disable time, so that one missed row cannot outlive a disable.

The audit gap is the other lasting lesson. Tetsu's real break-glass path is "holds the database credential", and right now that path records what changed but not who changed it. Recording an asserted actor and an outcome now costs a few fields. Leaving them out means the most privileged actions in the system stay the least attributable until per-operator logins or a logged-in admin page arrive.
