# Postgres database design: a practice review

Research on 2026-11-14 into Tetsu's Postgres design as of commit `f7624a1`: isolation and roles, schema and
migrations, the outbox, inbox, and audit record, the sessions table, and connections and operations. It feeds
[ADR-0060](../adr/0060-database-hardening.md) and [#22](https://github.com/heavymedl-labs/tetsu/issues/22).

## Summary

Tetsu's Postgres design is ahead of published practice on tenant isolation and migration safety, and its weak points sit elsewhere: a server floor that two-day-old security releases have overtaken, a few schema shapes that get expensive once real rows exist, an outbox dispatcher that holds a transaction open across consumer work, and connections with no bound once a query is in flight. The most urgent item is verified: **PostgreSQL 18.7 shipped on 2026-11-12 and fixes 52 vulnerabilities, including four that touch the exact row-level security and definer-function machinery Tetsu relies on**, while `migrate.rs` and CI still pin 18.6. The changes with the steepest cost curve are schema changes that are nearly free today, because only tenancy's and audit's migrations have been applied anywhere (the demo, on fictional data), and identity's and the outbox's have not: give `tenancy.locations` a real row id, add database CHECKs for rules only Rust enforces today, decide audit partitioning before the unique key on `event_id` locks it out, and make the outbox and session table changes before those files are first applied and frozen by the runner's drift check. The database runs on **Neon's free plan (Postgres 18, aws-us-east-2, direct endpoint, no pooler), with the app on Render's free web service**; Render's free Postgres was rejected because it expires after 30 days with no backups (`docs/adr/0012-first-hosting-and-deploys.md`). Nothing here argues for a rewrite; it argues for about a dozen targeted changes, ordered below by severity and by how much harder each gets once real data exists.

## Isolation beats every public checklist, but the server floor is two days stale

**The tenant boundary matches or exceeds every pitfall list surveyed.** Tetsu sets role, timeouts, and `app.tenant_id` with `set_config(..., true)` in one round trip per transaction, clears a stale tenant even in tenant-less transactions, and bans session-level `SET` with a lint; 2025 and 2026 guides converge on exactly this transaction-scoped pattern, while AWS's canonical 2020 post still set tenant context at session scope ([AWS](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/), [Bytebase](https://www.bytebase.com/blog/postgres-row-level-security-footguns/)). The policy predicate `tenant_id = (SELECT nullif(current_setting('app.tenant_id', true), ''))::bigint` is the initPlan form Supabase recommends, fails closed on the empty string a finished `SET LOCAL` leaves behind, and uses the leakproof `int8eq` so the tenant filter stays index-usable ([Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)). The permissive plus restrictive policy pair is real defense in depth, since permissive policies OR together and only a restrictive copy pins the tenant rule if a later policy widens access ([PG18 RLS](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)). The allowlist catalog check in `crates/postgres/sql/isolation_violations.sql` asserts exact policy text, forced RLS, `tenant_id`-led keys and composite foreign keys, `security_invoker` views, definer-function owners and `search_path`, and the full role graph. That covers far more than Supabase's splinter lints, the best-known public equivalent ([Supabase Database Advisors](https://supabase.com/docs/guides/database/database-advisors)). The lookup functions follow the manual's recipe for safe `SECURITY DEFINER` functions, with `search_path = pg_catalog, pg_temp`, EXECUTE revoked from PUBLIC, and narrow NOLOGIN owners ([PG18 CREATE FUNCTION](https://www.postgresql.org/docs/18/sql-createfunction.html)). Pinning `pg_temp` last is safer than Supabase's advice of an empty `search_path`, which leaves the temporary schema implicitly first.

**The 18.7 release is confirmed, and it makes the 18.6 floor insufficient.** The postgresql.org news archive carries "PostgreSQL 18.7, 17.12, 16.16, 15.20, 14.25, and 19 RC 2 Released!", dated **November 12, 2026**, and the announcement says it "fixes 52 security vulnerabilities" ([announcement](https://www.postgresql.org/about/news/postgresql-187-1712-1616-1520-1425-and-19-rc-2-released-3442/)). All four CVE identifiers in the research note appear on the security page as fixed in 18.7 ([PostgreSQL security](https://www.postgresql.org/support/security/)), with titles that match the note:

| CVE | What it breaks | CVSS | Why it matters to Tetsu |
| --- | --- | --- | --- |
| [CVE-2026-116311](https://www.postgresql.org/support/security/CVE-2026-116311/) | `DROP OWNED` removes restrictive RLS policies from tables the role does not own | 5.4 | Every tenant table carries a restrictive policy `TO tetsu_<schema>` |
| CVE-2026-116327 | `security_barrier` analysis exposes hidden values through indirect expressions | 4.3 | Same mechanism that keeps RLS quals ahead of user predicates |
| [CVE-2026-120154](https://www.postgresql.org/support/security/CVE-2026-120154/) | `INSERT ... ON CONFLICT` reads rows despite RLS | 4.3 | Not reachable today (only `DO NOTHING` on insert-only inbox tables), but one `DO UPDATE` in a module with UPDATE rights would expose it |
| [CVE-2026-116316](https://www.postgresql.org/support/security/CVE-2026-116316/) | Security-restricted operations plant types in `pg_temp` that later unqualified casts resolve to | 8.8 | Tetsu's SQL is full of unqualified `::bigint` and `::uuid` casts |

The same release also fixes CVE-2026-120146 (`REASSIGN OWNED` bypasses role SET checks) and CVE-2026-116303 (cast functions bypass EXECUTE). The existing floor exists for CVE-2026-14666, which the security page lists as fixed in 18.6, so the 18.6 floor did cover it ([PostgreSQL security](https://www.postgresql.org/support/security/)). Tetsu's pattern of per-transaction role switching, role-specific policies, and cached prepared statements on long-lived connections is the exact precondition set of the plan-cache CVE family (CVE-2024-10976, CVE-2026-14666), so the floor is load-bearing and should track every RLS or role advisory ([CVE-2024-10976](https://www.postgresql.org/support/security/CVE-2024-10976)). One caution changes how to do it: `migrate.rs` refuses older servers, so raising the floor before Neon runs 18.7 would stop deploys. Check the demo's `SHOW server_version` first, and bump the CI and benchmark images (`postgres:18.6` in `.github/workflows/ci.yml` and `benchmarks.yml`) in the same change. The announcement lists post-update REINDEX steps only for GIN, `gist_trgm_ops`, and `bpchar` B-tree indexes, none of which Tetsu has.

**Two grants are wider than the design intends.** First, the catalog check allows PUBLIC `CONNECT` and `TEMPORARY` on the database (`isolation_violations.sql` line 1107). The demo runbook already revokes `TEMPORARY`, and the manual singles out the temporary schema as the classic attack surface for definer functions, which CVE-2026-116316 just demonstrated again, so the check should enforce the revoke. Second, `prepare_module` grants `tetsu_delivery` to the request login `tetsu_app` (`crates/postgres/src/roles.rs` line 95). Injected SQL on the request path could `SET ROLE tetsu_delivery` and read every tenant's outbox payloads in one query, because that role has a `USING (TRUE)` policy. ADR-0042 already gave the operator role its own login and pool for this reason, and the dispatcher deserves the same. This is bulk-exfiltration reduction rather than a new hole: injection can already walk tenants one at a time by changing `app.tenant_id`, which is a design property experts have accepted since Vondra's 2016 analysis ([EDB](https://www.enterprisedb.com/blog/application-users-vs-row-level-security)). ADR-0042 states that honest scope for roles, and the same sentence belongs beside the policy text: RLS here catches missing filters and bugs, not injected SQL.

## Four schema shapes get expensive the day real rows exist

**`tenancy.locations` has no row id.** Its primary key is `(tenant_id, sort_order)` (`crates/tenancy/migrations/0001_tenants.sql` line 27), which breaks ADR-0042's own rule that tenant-owned keys are `(tenant_id, id)` with uuidv7 ids. The catalog check only tests that a key starts with `tenant_id`, so it misses this. Every future table that references a location (bookings, staff schedules) would carry a mutable display order as its foreign key and cascade renumbering on every reorder. The fix is `id uuid DEFAULT uuidv7()`, key `(tenant_id, id)`, and `UNIQUE (tenant_id, sort_order) DEFERRABLE INITIALLY DEFERRED` so a reorder can swap positions in one transaction. Today it costs a migration and a demo reseed; later it costs a rewrite of every referencing table. The rest of the key mix is coherent and worth writing down as a rule: bigint identity for global registry rows, uuidv7 for tenant-owned and event rows, and v4 for values that must reveal neither time nor order (`sessions.id`, WebAuthn `user_handle`), which is the case RFC 9562 reserves for v4 ([RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html#name-security-considerations)). The uuidv7 choice is well supported: on PG 18, credativ measured 50 million inserts at about 1:46 with v7 versus 20:40 with v4, with about 90% versus 71% leaf density ([credativ](https://www.credativ.de/en/blog/postgresql-en/a-deeper-look-at-old-uuidv4-vs-new-uuidv7-in-postgresql-18/)).

**Rust is the only guard on most column rules.** Slugs, `#RRGGBB` colors, 1 to 100 character names, address normalization, and JSONB payloads have no CHECK; only `sessions.token_hash` length and `sessions.realm` do. GitLab's migration guide requires a limit on every text, bytea, and jsonb column ([GitLab](https://docs.gitlab.com/development/migration_style_guide/)), and ADR-0042's "the database is the backstop" reasoning applies just as well here. Add `slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$' AND octet_length(slug) <= 63`, which also makes case-insensitive uniqueness automatic, color and name-length checks, and `jsonb_typeof(payload) = 'object' AND octet_length(payload::text) <= N` on audit and outbox payloads. Now these are one-line edits; later each needs `NOT VALID`, a cleanup of bad rows, and `VALIDATE`. Two traps follow. `LIKE ... INCLUDING DEFAULTS`, which builds `records` and `outbox` from their global twins, does not copy CHECKs, so add `INCLUDING CONSTRAINTS` or repeat them. And `locations.time_zone` cannot be validated by a CHECK, which cannot contain subqueries ([PG18 CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html)), so it holds whatever text arrives until open decision #21 lands; validating on insert with `now() AT TIME ZONE $1` stops bad values accumulating. For identifier keys (`slug`, `address`), `COLLATE "C"` is "efficient and stable across all versions" ([PG18 collation](https://www.postgresql.org/docs/18/collation.html)), so it removes index risk from collation library upgrades for a one-line change now. Case-insensitive customer email should be a normalized key column, not citext, which the extension ban forbids, nor a nondeterministic collation, which costs B-tree deduplication.

**Audit's unique key blocks time partitioning.** `audit.records` has `UNIQUE (tenant_id, event_id)`, and every unique constraint on a partitioned table must include the partition key ([PG18 CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html)). Partitioning by time for retention would therefore turn the key into one that no longer guarantees one row per event, leaving the inbox as the only dedupe. Choose before data lands: drop the unique and rely on the inbox, keep it and give up time partitions, or hash-partition by tenant, which keeps the key but does not help retention. Declaring the table partitioned from the start is cheap now; converting later means a new parent, attach, and RLS and grants on each partition.

**Bookings will need `btree_gist`.** PG 18's `WITHOUT OVERLAPS` keys are the natural fit for appointments, and the manual says the non-range columns need GiST equality, with `btree_gist` "the expected way to use this feature" ([PG18 CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html)). The catalog check forbids every extension but plpgsql, so a `(tenant_id, room, period WITHOUT OVERLAPS)` key is impossible today. Settle it in an ADR before the scheduling schema exists; the fallback, application locks, is weaker. Host support for `btree_gist` on Neon and future paid hosts was not checked.

**The runner is above the bar, with three gaps.** A polled advisory lock, exact-text drift detection, per-file transactions, single-statement no-transaction files with an invalid-index check, and Squawk in CI exceed what refinery or the SQLx migrator offer. The gaps are timeouts set only by convention in each file, no retry on `lock_not_available` (55P03), and frozen shared templates. strong_migrations and postgres.ai both treat a short lock timeout plus retries with backoff and jitter as the core safeguard, since a DDL waiting for `ACCESS EXCLUSIVE` blocks every later query on the table, plain SELECTs included ([strong_migrations](https://github.com/ankane/strong_migrations), [postgres.ai](https://postgres.ai/blog/20210923-zero-downtime-postgres-schema-migrations-lock-timeout-and-retries)). Because each file is one transaction or one statement, retrying the whole file is about a dozen lines. The frozen templates matter more than they look: `outbox.sql` and `inbox.sql` are embedded as each consumer module's own version, and the runner compares exact text, so after first application any edit, even a comment, breaks every module that applied them. Audit already applied `inbox.sql` on the demo, so it is frozen there; make every outbox change listed below before `outbox.sql` reaches the demo, and version later changes as new template files. PG 18's `NOT NULL ... NOT VALID` gives expand and contract a native path for new required columns, replacing the CHECK-then-SET-NOT-NULL sequence strong_migrations still teaches ([PG 18 release notes](https://www.postgresql.org/docs/release/18.0/)).

## The outbox holds a transaction open for up to 90 seconds

**The claim query is textbook; the transaction around it is not.** `ORDER BY due_at LIMIT 50 FOR UPDATE SKIP LOCKED` over a partial index on undelivered rows is the standard shape, and in-process wake-ups instead of `NOTIFY` sidestep the commit-time lock that caused three Recall.ai outages in March 2025 ([Recall.ai](https://www.recall.ai/blog/postgres-listen-notify-does-not-scale)). Selecting by state rather than by an id cursor also avoids the commit-order gap that sequences and uuidv7 share ([event-driven.io](https://event-driven.io/en/ordering_in_postgres_outbox/)). The problem is that `deliver_from` keeps its claiming transaction open while consumers run on other pooled connections, for up to `PASS_LIMIT` (60 s) plus one 30 s `APPLY_TIMEOUT` (`crates/postgres/src/events.rs`). A transaction holding an xid pins the database-wide vacuum horizon for every table, not only the outbox. PlanetScale's 2026 benchmark on Postgres 18 showed overlapping long transactions driving a queue to 383,000 dead tuples and 300 ms lock times, against 2 ms when overlap was capped ([PlanetScale](https://planetscale.com/blog/keeping-a-postgres-queue-healthy)). A May 2026 incident saw queue selection cross 1 s at about 4 million dead tuples ([Stormatics](https://stormatics.tech/blogs/long-running-transactions-job-queues-and-the-cascade-that-wreaks-havoc)). At demo volume the harm is small; it grows with webhooks and email. The fix is claim, process, settle in separate short transactions: claim with `UPDATE ... SET due_at = clock_timestamp() + lease, attempts = attempts + 1 ... RETURNING` over the `SKIP LOCKED` subquery and commit, run consumers with no outbox transaction open, then settle each row in its own statement. The lease replaces the row lock, and a crash just lets it expire.

**Stopped events stay in the hot index forever, and delivered rows churn twice.** Rows that exhaust 10 attempts without `keep` keep `delivered_at IS NULL`, so they stay in `outbox_due` with the oldest `due_at` values, and every poll walks past them. Settling updates `delivered_at`, which appears in the partial index predicate, and retries update the indexed `due_at`, so neither update can be HOT ([PG18 HOT](https://www.postgresql.org/docs/18/storage-hot.html)). Each delivered event costs a non-HOT update now and a delete seven days later, and fillfactor cannot help. One merged fix covers the bloat: add `stopped_at` to the index predicate (or move stopped rows to a dead-letter table, as pg-boss v10 does ([pg-boss](https://github.com/timgit/pg-boss/releases/tag/10.0.0))), delete at settle since ADR-0043 already says the outbox is not history (or batch the seven-day delete), set per-table autovacuum thresholds, and re-alert kept events that keep failing, since `event_stopped` fires only once at exactly 10 attempts.

**The inbox is the textbook idempotent consumer but has no retention.** Recording the event id in the consumer's schema with `ON CONFLICT DO NOTHING`, in the same transaction as the effect, is the pattern microservices.io and Azure document ([microservices.io](https://microservices.io/patterns/communication-style/idempotent-consumer.html)). Rows grow forever, though, and settlement is per event rather than per consumer, so an event kept for one failing consumer is redelivered to every other consumer on each retry. Pruning their inbox rows by age would then re-apply effects. Before any pruning, Audit's `record.sql` and `record_global.sql` need `ON CONFLICT ... DO NOTHING`; otherwise a redelivery hits the unique key, Audit fails forever, and the event retries hourly without end. Per-consumer delivery rows are the clean fix when webhooks arrive.

**The audit record is append-only by grant alone, which falls short of ASVS 5.0 Level 2.** `REVOKE ALL; GRANT SELECT, INSERT` stops the runtime role, but the record sits in the same database it audits, alterable by the owner, and nothing ships it elsewhere. ASVS 5.0 requires that logs "cannot be modified" (16.4.2), are "securely transmitted to a logically separate system" (16.4.3), and have documented retention periods (16.1.1) ([OWASP ASVS V16](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md)). The outbox makes the external copy cheap: one more never-lose consumer that ships each record to the OTLP logs backend now, and to object storage with object lock once a provider is chosen. Blocking triggers on UPDATE and DELETE, plus a separate `BEFORE TRUNCATE` statement trigger because row triggers skip TRUNCATE, stop migration mistakes and casual owner edits, though owners can still disable them ([dev.to/gentlyding](https://dev.to/gentlyding/stop-trusting-the-app-enforcing-append-only-at-the-database-layer-1bkm)). Given the external copy is needed anyway, an in-database HMAC chain is optional. The split between tenant and global tables, and the rule that payloads carry ids and facts but never personal details, are both sound and worth keeping.

## Connections have no bound once a query is sent

**A stalled network can hold a request and a pool slot for minutes to hours.** Pool `wait_timeout` (2 s) and `create_timeout` (5 s) cover only acquiring a connection. `statement_timeout` is enforced by the server, whose error may never arrive across a black-holed Render to Neon path, and tokio-postgres's default keepalive idle is **2 hours** with `tcp_user_timeout` unset ([tokio-postgres Config](https://docs.rs/tokio-postgres/latest/tokio_postgres/config/struct.Config.html)). Set `tcp_user_timeout` around 10 to 15 s and tighter keepalives on the `Config`, wrap each scoped transaction in a client timeout a little above `statement_timeout`, and drop the connection when it fires. ADR-0055's stall test should assert that bound.

**One merged change covers every whole-transaction timeout note.** Add `idle_in_transaction_session_timeout` and PG 17's `transaction_timeout` to the startup options beside `statement_timeout` (for example 10 s and 15 s, with the delivery login set to cover its longest legitimate pass, or shorter once the lease change lands). These are the documented backstops against an open transaction that holds back vacuum and keeps role and tenant set on a pooled connection ([PG18 client config](https://www.postgresql.org/docs/18/runtime-config-client.html)). Map their codes 25P03 and 25P04, and the closed connection they leave, to Temporary. Do not set `idle_session_timeout`, which the manual warns against for pooled connections. `RecyclingMethod::Fast` is acceptable because every scoped transaction resets its own state, but Neon free suspends after 5 minutes idle and always scales to zero ([Neon plans](https://neon.com/docs/introduction/plans)), so evict pooled connections idle longer than about 4 minutes, or retry once a not-yet-committing transaction that fails on a dead checked-out connection. `Clean` recycling buys nothing here.

**Error classes need one addition.** `sort_commit` already handles an unknown commit outcome the way Jepsen's evidence demands, never retrying it blindly ([Jepsen](https://aphyr.com/posts/282-jepsen-postgres)). What is missing is a Conflict class for 40001, 40P01, and 55P03, retried as a whole transaction with jitter, which the manual says is the only correct retry unit ([PG18 serialization failures](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)).

**The sessions table is sound; one merged change prepares it for load.** Hash-only token storage, a separate v4 public id, one clock read, a race-safe `greatest()`, and a pinned definer `search_path` beat common practice ([Copenhagen Book](https://copenhagen.pilcrowonpaper.com/sessions)). The per-request `last_seen_at` update is HOT-eligible because that column is unindexed, but default fillfactor 100 leaves no room on the page. The single sessions recommendation therefore has four parts. Set `fillfactor = 80` in the unapplied `0001_operators.sql`, and add a test that forbids indexing `last_seen_at`. Add a sweep on `ends_at`, driven by the app rather than pg_cron, which on Neon runs only while the compute is awake ([Neon pg_cron](https://neon.com/docs/extensions/pg_cron)). Throttle the write to once a minute when customer realms arrive, as ADR-0059 plans for slice 7. Make `sessions → operators` `ON DELETE CASCADE`. Do not make the table UNLOGGED: on Neon it would empty every time the compute idles ([Neon compatibility](https://neon.tech/docs/reference/compatibility)).

**TLS is stronger than its label.** The rustls connector verifies chain and hostname, so `SslMode::Require` behaves like libpq's `verify-full`, plus channel binding on Neon ([PG18 libpq SSL](https://www.postgresql.org/docs/18/libpq-ssl.html)). Say so in ADR-0013 and the code so nobody "fixes" it, add a hostname-mismatch test, and enforce channel binding in code rather than trusting the URL. For production, Render's PITR reaches 7 days only on Pro workspaces and cannot target the last 10 minutes ([Render backups](https://render.com/docs/postgresql-backups)), so ADR-0045's external daily dump stays necessary. Neon free gives a 6-hour restore window, enough for the demo.

## Conclusion

The pattern across all four areas is the same: where Tetsu wrote a rule down and made the catalog check enforce it, it leads practice; where a rule lives only in Rust, in a per-file convention, or in an unstated assumption about volume, it trails. The cheapest way to keep the lead is to move rules from the second group to the first while the tables are still empty: CHECKs in the schema, timeouts in the runner and the connection, and the version floor tied to the advisory feed.

The window is unusually concrete. Only tenancy's and audit's migrations have been applied anywhere, on the demo's fictional data, so identity and the outbox can still change by editing their first files, and audit and the inbox by a new migration or a demo reset. Once the runner's drift check freezes those files and the first real business stores data, most items in the "do now" table turn from edits into projects. The 18.7 floor is the exception; it never gets harder, but every day on 18.6 leaves four known RLS and definer-function bugs open on the boundary the whole design depends on.
