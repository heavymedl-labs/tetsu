# WebAuthn RP ID mechanics, Related Origin Requests, and embedding (as of 2026-11-11)

Primary spec: W3C Web Authentication Level 3. It became a W3C **Recommendation on 25 August 2026** (<https://www.w3.org/TR/2026/REC-webauthn-3-20260825/>). Its status section says "There have been no substantive changes since the Candidate Recommendation Snapshot of 26 May 2026." Spec quotes below come from the text downloaded from <https://www.w3.org/TR/webauthn-3/> on 2026-11-11. Browser support data comes from MDN browser-compat-data (BCD) `main` as of commit date 2026-11-11, passkeys.dev (last updated 21 Sep 2026), web.dev, and developer.chrome.com.

## RP ID rules: registrable domain suffix, subdomains, ports, PSL, effective domain

### Takeaway

An RP ID is a bare domain with no scheme or port. It must equal the caller's effective domain or be a registrable domain suffix of it, and that rule depends on the Public Suffix List. `onrender.com` **is on the PSL** (private section, submitted by Render), so `tetsu-demo.onrender.com` can only use the RP ID `tetsu-demo.onrender.com`. Passkeys made there can never be shared with a future Tetsu domain, except through Related Origin Requests, which would have to be served from the RP ID host.

### Cited Findings

- Definition: "a relying party identifier is a valid domain string identifying the WebAuthn Relying Party on whose behalf a given registration or authentication ceremony is being performed. A public key credential can only be used for authentication with the same entity (as identified by RP ID) it was registered with." — [WebAuthn L3 §4 Terminology, "Relying Party Identifier"](https://www.w3.org/TR/webauthn-3/#rp-id)
- Default and override: "By default, the RP ID for a WebAuthn operation is set to the caller's origin's effective domain. This default MAY be overridden by the caller, as long as the caller-specified RP ID value is a registrable domain suffix of or is equal to the caller's origin's effective domain." — [WebAuthn L3 §4](https://www.w3.org/TR/webauthn-3/#rp-id)
- Scheme and port: "An RP ID is based on a host's domain name. It does not itself include a scheme or port, as an origin does. The RP ID of a public key credential determines its scope." The origin must satisfy all of these: "The RP ID must be equal to the origin's effective domain, or a registrable domain suffix of the origin's effective domain." Also, one of these must be true: "The origin's scheme is https." or "The origin's host is localhost and its scheme is http." Finally: "The origin's port is unrestricted." — [WebAuthn L3 §4](https://www.w3.org/TR/webauthn-3/#rp-id)
- Spec example: "given a Relying Party whose origin is <https://login.example.com:1337>, then the following RP IDs are valid: login.example.com (default) and example.com, but not m.login.example.com and not com. Another example of a valid origin is <http://localhost:8000>". The rationale given is "This is done in order to match the behavior of pervasively deployed ambient credentials (e.g., cookies, [RFC6265])." — [WebAuthn L3 §4](https://www.w3.org/TR/webauthn-3/#rp-id)
- Effective domain checks in create and get: "Let callerOrigin be origin. If callerOrigin is an opaque origin, throw a 'NotAllowedError' DOMException. Let effectiveDomain be the callerOrigin's effective domain. If effective domain is not a valid domain, then throw a 'SecurityError' DOMException." The note adds: "Only the domain format of host is allowed here", so IP addresses are rejected. — [WebAuthn L3 §5.1.3 and §5.1.4](https://www.w3.org/TR/webauthn-3/#sctn-createCredential)
- In create, if `rp.id` "is not a registrable domain suffix of and is not equal to effectiveDomain" and the client supports related origin requests, the client runs the related origins validation procedure. If it "does not support related origin requests", the client must "throw a 'SecurityError' DOMException". If `rp.id` is absent, the client sets it to effectiveDomain. `get()` does the same with `rpId`. — [WebAuthn L3 §5.1.3](https://www.w3.org/TR/webauthn-3/#sctn-createCredential), [§5.1.4](https://www.w3.org/TR/webauthn-3/#sctn-getAssertion)
- "Registrable domain suffix" comes from the HTML spec and rests on the PSL. The spec's own example of the "registrable origin label" says: "the registrable origin label of both example.co.uk and <www.example.de> is example if both co.uk and de are public suffixes." — [WebAuthn L3 §4, "Registrable Origin Label"](https://www.w3.org/TR/webauthn-3/#registrable-origin-label)
- **`onrender.com` is on the PSL.** The list at VERSION 2026-11-10_11-23-57_UTC (commit 3db7776283b0874634fea8b01168f785360d64f2) contains, in its private-domains section: `// Render : https://render.com` / `// Submitted by Anurag Goel <dev@render.com>` / `onrender.com` / `app.render.com`. — [publicsuffix.org list](https://publicsuffix.org/list/public_suffix_list.dat)

### Inferences

- `onrender.com` is a public suffix, so `tetsu-demo.onrender.com` is itself a registrable domain (eTLD+1). Its only valid RP ID is `tetsu-demo.onrender.com`. `onrender.com` would be rejected as an RP ID, just as `com` is.
- Paths play no part. Every business at `/<slug>` on one host shares one RP ID, and the spec has no per-path scoping.
- On Tetsu's own domain, say `tetsu.example`, the RP ID `tetsu.example` would cover `tetsu.example`, `app.tetsu.example`, `<slug>.tetsu.example`, and any port. Subdomain-per-tenant hosting keeps one shared passkey per user across tenants, provided the RP ID is set to the apex.
- A custom business domain, such as `book.acmesalon.com`, cannot use `tetsu.example` as an RP ID through the suffix rule. It needs Related Origin Requests, and the label cap rules that out at multi-tenant scale. Otherwise login must happen on a Tetsu origin, through a redirect, a popup, or an iframe.
- Passkeys made on `tetsu-demo.onrender.com` are tied to that RP ID for good. Moving to Tetsu's own domain needs re-enrolment, unless the new domain's pages call WebAuthn with `rpId: "tetsu-demo.onrender.com"` through Related Origin Requests. That requires serving `/.well-known/webauthn` on `tetsu-demo.onrender.com` for as long as those passkeys are in use.

### Gaps

- I did not quote the HTML spec's "is a registrable domain suffix of or is equal to" algorithm directly. I inferred its PSL dependence from the WebAuthn label definition and from prior knowledge of the HTML spec's use of "registrable domain", which is defined through the PSL.
- I have not checked whether browsers snapshot the PSL at build time and how stale those snapshots can be. That is prior knowledge: Chromium and Firefox ship a built-in copy.

## Related Origin Requests (/.well-known/webauthn)

**Takeaway:**
The RP ID host serves `https://<rpid>/.well-known/webauthn` as JSON with an `origins` array. Clients "MUST support at least five registrable origin labels", and Chrome caps it at exactly 5. Chrome and Edge 128+ and Safari 18 (macOS 15, iOS 18) support it. Firefox's status conflicts: passkeys.dev lists Firefox 152+, while web.dev in January 2026 said Firefox was "still considering". The feature exists for ccTLD and brand variants of one company. It is not meant for an unbounded set of tenant domains.

**Cited Findings:**

- Motivation: the default rule "can make deployment challenging for large environments where multiple country-specific domains are in use (e.g. example.com vs example.co.uk vs example.sg), where alternative or brand domains are required (e.g. myexampletravel.com vs examplecruises.com), and/or where platform as a service providers are used to support mobile apps." — [WebAuthn L3 §5.11](https://www.w3.org/TR/webauthn-3/#sctn-related-origins)
- "WebAuthn Relying Parties can opt in to allowing WebAuthn Clients to enable a credential to be created and used across a limited set of related origins. Such Relying Parties MUST choose a common RP ID to use across all ceremonies from related origins." — [WebAuthn L3 §5.11](https://www.w3.org/TR/webauthn-3/#sctn-related-origins)
- "A JSON document MUST be hosted at the webauthn well-known URL [RFC8615] for the RP ID, and MUST be served using HTTPS. ... The content type MUST be application/json. The top-level JSON object MUST contain a key named origins whose value MUST be an array of one or more strings containing web origins." — [WebAuthn L3 §5.11](https://www.w3.org/TR/webauthn-3/#sctn-related-origins)
- **Label minimum:** "WebAuthn Clients supporting this feature MUST support at least five registrable origin labels. Client policy SHOULD define an upper limit to prevent abuse." — [WebAuthn L3 §5.11](https://www.w3.org/TR/webauthn-3/#sctn-related-origins)
- Fetch rules: "Requests to this well-known endpoint by WebAuthn Clients MUST be made without credentials, without a referrer, and using the https: scheme. When following redirects, WebAuthn Clients MUST explicitly require all redirects to also use the https: scheme." Also, clients "SHOULD include relatedOrigins in their response to getClientCapabilities()." — [WebAuthn L3 §5.11](https://www.w3.org/TR/webauthn-3/#sctn-related-origins)
- Validation algorithm (§5.11.1), verbatim steps. "Let maxLabels be the maximum number of registrable origin labels allowed by client policy." Fetch `https://rpIdRequested/.well-known/webauthn`. "If the fetch fails, the response does not have a content type of application/json, or does not have a status code (after following redirects) of 200, then throw a 'SecurityError'". Then, for each originItem: parse the URL; "Let domain be the effective domain of url"; "Let label be registrable origin label of domain"; "If label is empty or null, continue."; "If the size of labelsSeen is greater than or equal to maxLabels and labelsSeen does not contain label, continue."; "If callerOrigin and url are same origin, return true."; "If the size of labelsSeen is less than maxLabels, append label to labelsSeen." Finally "Return false." — [WebAuthn L3 §5.11.1](https://www.w3.org/TR/webauthn-3/#sctn-validating-relation-origin)
- The count is per registrable origin label, the part before the public suffix. It is not per origin. The spec's example lists 10 origins (`example.co.uk`, `example.de`, `example.sg`, `example.net`, `exampledelivery.com` and its variants, `myexamplerewards.com`, `examplecars.com`), but they span only 4 labels. Matching needs the exact origin, same origin, so the scheme, host, and port must all match. — [WebAuthn L3 §5.11](https://www.w3.org/TR/webauthn-3/#sctn-related-origins)
- Chrome: "the maximum number of labels is 5". Each origin reduces to its eTLD+1 label: `example.co.uk` and `example.de` both count as `example`, and `example-rewards.com` counts as `example-rewards`. Origins past the limit are ignored. As of January 2026, Chrome and Safari support it and "Firefox is still considering the feature." — [web.dev, Allow passkey reuse across your sites with Related Origin Requests](https://web.dev/articles/webauthn-related-origin-requests)
- Chrome shipped Related Origin Requests alongside hints and JSON serialization. — [Chrome blog, passkeys updates in Chrome 129](https://developer.chrome.com/blog/passkeys-updates-chrome-129)
- passkeys.dev (last updated 21 Sep 2026) lists Related Origin Requests support as Chrome/Edge 128+ on Android, ChromeOS, macOS, Ubuntu, and Windows; Safari on macOS 15+; iOS/iPadOS 18+; and **Firefox 152+**. The table is flattened in the fetched text, so the cell mapping is inferred. — [passkeys.dev device support](https://passkeys.dev/device-support/); this conflicts with [web.dev](https://web.dev/articles/webauthn-related-origin-requests) ("still considering", January 2026). A third-party blog also claims Firefox 152 shipped it in May 2026 — [MojoAuth blog](https://mojoauth.com/blog/related-origin-requests-passkeys-across-cctlds.md) (unverified). A Mozilla support thread reports it failing on Firefox 140 — [support.mozilla.org](https://support.mozilla.org/de/questions/1600732).
- MDN BCD has no entry for Related Origin Requests, so it cannot settle the question. I checked `api/PublicKeyCredential.json`, `CredentialsContainer.json`, and `Permissions-Policy.json` for "related". — [mdn/browser-compat-data](https://github.com/mdn/browser-compat-data)
- Native apps are a separate system. To share passkeys between a website and an app, use Digital Asset Links on Android and Chrome, and Associated Domains on Apple platforms. — [web.dev ROR article](https://web.dev/articles/webauthn-related-origin-requests)
- Privacy and UI: when the caller origin and RP ID differ, clients "SHOULD ensure that the credential and authenticator selection interfaces provide clear context to the user by displaying both" the caller's origin and the RP ID. An example prompt: "Sign in to otherExampleB.com with your passkey for exampleA.com?" — [WebAuthn L3 §14.5.5](https://www.w3.org/TR/webauthn-3/#sctn-cross-origin-privacy)

**Inferences:**

- In Chrome, the 5-label cap cannot be raised by the RP. It rules Related Origin Requests out as a way to let many businesses' custom domains share Tetsu's RP ID. Five custom-domain tenants would use up the budget. Origins past the fifth label are silently ignored, so later tenants would just fail.
- Related Origin Requests can serve as a bridge for one domain move. List the new Tetsu origin in `https://tetsu-demo.onrender.com/.well-known/webauthn` and keep using RP ID `tetsu-demo.onrender.com` from the new domain. The new domain would then depend on the Render host forever, which is a poor trade for a demo-stage product. The reverse is simpler: pick the final RP ID before real users enrol.
- Browsers without support throw `SecurityError`, so an RP would need a fallback such as redirecting to the RP ID origin. It can feature-detect through `getClientCapabilities()` and check `relatedOrigins`.
- Native apps and third-party password managers do not fetch `/.well-known/webauthn` themselves on the web. The browser does the check, then hands the RP ID to the provider. This is inferred from the spec placing the procedure in the WebAuthn Client. I found no source on how 1Password or Bitwarden extensions, which wrap WebAuthn in the page, handle it.

**Gaps:**

- I found no primary Mozilla source, such as release notes or a Bugzilla bug, confirming Firefox shipped Related Origin Requests. Treat "Firefox 152+" as likely but unverified.
- I found no source on Related Origin Requests behaviour in extension-based password managers (1Password, Bitwarden) or in native iOS and Android credential APIs. I also found no Safari label limit; Safari's cap is undocumented in what I read.
- From prior knowledge, unverified here: Chrome's implementation is 128 on desktop, and Android shipped later. passkeys.dev lists Android Chrome 128+.

## Passkeys inside iframes (Permissions Policy, cross-origin create and get)

**Takeaway:**
WebAuthn is off by default in cross-origin iframes. The embedder delegates it with `allow="publickey-credentials-get"` and `allow="publickey-credentials-create"`. Cross-origin **create** also needs transient user activation and cannot use conditional mediation. The iframe's own origin sets the RP ID, so a Tetsu iframe on a business's site uses Tetsu's RP ID. Support differs by browser and the sources conflict. Chrome supports get, and create since M123. Firefox supports get from 118 and create from 123. Safari's support is the weakest and least clearly documented.

**Cited Findings:**

- "This specification defines two policy-controlled features identified by the feature-identifier tokens 'publickey-credentials-create' and 'publickey-credentials-get'. Their default allowlists are both 'self'." Also: "If disabled in any document, no content in the document will be allowed to use the foregoing methods". — [WebAuthn L3 §5.9](https://www.w3.org/TR/webauthn-3/#sctn-permissions-policy)
- "The Web Authentication API is disabled by default in cross-origin iframes. To override this default policy ... specify the allow attribute on the iframe element and include the publickey-credentials-create or publickey-credentials-get feature-identifier token, respectively, in the allow attribute's value." — [WebAuthn L3 §5.10](https://www.w3.org/TR/webauthn-3/#sctn-iframe-guidance)
- Cross-origin create, from the [[Create]] steps: "If sameOriginWithAncestors is false: If options.mediation is present with the value conditional: Throw a 'NotAllowedError' DOMException. If the relevant global object ... does not have transient activation: Throw a 'NotAllowedError' DOMException. Consume user activation of the relevant global object. If the origin that is creating a credential is different from the top-level origin ... the client SHOULD make this fact clear to the user." — [WebAuthn L3 §5.1.3](https://www.w3.org/TR/webauthn-3/#sctn-createCredential)
- Client data records the embedding context through `crossOrigin` and the new `topOrigin` member. The RP "MUST validate that its value is expected". Valid policies include requiring topOrigin to equal origin, or to equal "some element of a list of allowed origins". — [WebAuthn L3 §5.8.1, §13.4.x](https://www.w3.org/TR/webauthn-3/#dom-collectedclientdata-toporigin)
- Clickjacking: "Simplistic use of WebAuthn in an embedded context ... may make users vulnerable to UI Redressing attacks". The spec suggests Intersection Observer v2 `isVisible` and falling back to a popup. — [WebAuthn L3 §13.4.2](https://www.w3.org/TR/webauthn-3/#sctn-seccons-visibility)
- Iframe privacy: clients SHOULD warn about the top-level origin. "A successful ceremony allows both the top-level origin and the calling origin to correlate the user's identity across their respective sites." — [WebAuthn L3 §14.5.5](https://www.w3.org/TR/webauthn-3/#sctn-cross-origin-privacy)
- Chrome cross-origin iframe create: the intent to ship targeted M122. On 23 Jan 2024 it was "retargeted ... to M123". It requires the permission policy and transient user activation. Gecko gave "No signal". For WebKit, "folks from Apple were against the proposal when discussed in the WebAuthn WG." — [blink-dev Intent to Ship](https://groups.google.com/a/chromium.org/g/blink-dev/c/Sq2WAVbPz6g)
- MDN BCD (main, 2026-11-11). For the iframe `allow` attribute: `publickey-credentials-get` is Chrome 84, Firefox 118, Safari false. `publickey-credentials-create` is Chrome false, Firefox 123, Safari false. For the `Permissions-Policy` header, both directives are Chrome 88 only, with Firefox and Safari false. — [BCD iframe.json](https://github.com/mdn/browser-compat-data/blob/main/html/elements/iframe.json), [BCD Permissions-Policy.json](https://github.com/mdn/browser-compat-data/blob/main/http/headers/Permissions-Policy.json). The "Chrome false" for create contradicts the Chrome M123 ship above and Chrome's header support, so BCD looks wrong or stale here.
- web.dev repeats the same tables. It tells embedders to send a `Permissions-Policy` header, e.g. `publickey-credentials-get=(self "https://embedded-auth.example.com")`, *and* to set the iframe `allow` attribute. Session cookies in the iframe need `SameSite=None; Secure; Partitioned`, so "users must sign in again for each embedding site". Limit framers with CSP `frame-ancestors`. — [web.dev, Passkeys within iframes](https://web.dev/articles/webauthn-within-iframe)
- A vendor source says Safari supports only authentication in cross-origin iframes, not registration. — [Corbado FAQ](https://corbado.com/blog/iframe-passkeys-webauthn/enable-passkeys-iframe) (vendor, not primary). This contradicts BCD's "Safari false" for the get `allow` token.

**Inferences:**

- A Tetsu iframe on `acmesalon.com` runs WebAuthn as Tetsu's origin with Tetsu's RP ID. Passkeys made in the iframe are the same passkeys used on Tetsu's site, so frames do not fragment credentials. Tetsu cannot set the `allow` attribute, though. Each business must paste embed code that includes it, and in Chrome the business's page must not send a `Permissions-Policy` header that blocks the feature.
- Even when the passkey ceremony succeeds, the session cookie in the frame is partitioned per embedding site, or blocked in Safari without the Storage Access API. Embedded login therefore gives a per-business session, not a Tetsu-wide one. The robust pattern is to open login in a top-level popup or redirect to the Tetsu origin, which is also what the spec's clickjacking guidance suggests.
- Registration in an iframe is the least portable path: it needs a user gesture, cannot be conditional, and is unclear in Safari. Plan to create passkeys first-party, on Tetsu's own origin.

**Gaps:**

- I could not confirm Safari's exact behaviour for cross-origin iframe get and create from WebKit sources, such as release notes or WebKit bugs. The sources conflict. From prior knowledge, unverified: Safari has allowed get in cross-origin iframes with `allow` since about Safari 16 or 17, and Firefox create landed in 123.
- I did not verify Edge separately. It is assumed to mirror Chrome, as BCD marks it "mirror".

## Conditional mediation (passkey autofill) across origins

**Takeaway:**
Conditional get works on the page's own origin and RP ID. It filters to discoverable credentials and waits for the life of the document. Conditional **create** (automatic passkey upgrade) is forbidden in cross-origin frames by the spec. The spec does not explicitly forbid conditional get in a cross-origin iframe, but I found no evidence that browsers support it there.

**Cited Findings:**

- Conditional get: "If options.mediation is present with the value conditional: Let credentialIdFilter be the value of pkOptions.allowCredentials. Set pkOptions.allowCredentials to empty. Note: This prevents non-discoverable credentials from being used during conditional requests. Set a timer lifetimeTimer to a value of infinity." — [WebAuthn L3 §5.1.4](https://www.w3.org/TR/webauthn-3/#sctn-getAssertion)
- Autofill trigger: the client acts when "the user interacts with an input or textarea form control with an autocomplete attribute whose non-autofill credential type is 'webauthn'". The "'webauthn' autofill detail token must appear immediately after the last autofill detail token of type 'Normal' or 'Contact'", e.g. `"username webauthn"`. — [WebAuthn L3 §5.1.4](https://www.w3.org/TR/webauthn-3/#sctn-getAssertion)
- Conditional create throws `NotAllowedError` when `sameOriginWithAncestors` is false. See the [[Create]] quote in the iframe section. — [WebAuthn L3 §5.1.3](https://www.w3.org/TR/webauthn-3/#sctn-createCredential)
- Support: `isConditionalMediationAvailable` is Chrome 108, Firefox 119, Safari 16. `create` `mediation` is Chrome 136 (Android 142), Safari 18, Firefox false. `getClientCapabilities` is Chrome 133, Firefox 135, Safari 17.4. — [MDN BCD PublicKeyCredential.json](https://github.com/mdn/browser-compat-data/blob/main/api/PublicKeyCredential.json), [CredentialsContainer.json](https://github.com/mdn/browser-compat-data/blob/main/api/CredentialsContainer.json). passkeys.dev agrees: conditional create is Chrome 136+ on desktop, Android 142+, iOS 18+, Safari 18+, and "Also requires support from credential managers and operating systems" — [passkeys.dev](https://passkeys.dev/device-support/)

**Inferences:**

- Autofill only offers passkeys whose RP ID matches the RP ID the request names. Each RP ID's passkeys show up in autofill only on origins valid for that RP ID: the suffix rule, or Related Origin Requests where supported. With one apex RP ID, autofill works on every Tetsu subdomain. On a business's custom domain, autofill would not offer Tetsu passkeys without Related Origin Requests.

**Gaps:**

- I found no source stating whether Chrome or Safari show conditional UI inside cross-origin iframes. I also found no source on whether conditional get works together with Related Origin Requests.

## Domain changes and migration (Related Origin Requests bridge, re-registration, Signal API)

**Takeaway:**
No WebAuthn mechanism moves a passkey to a new RP ID. A credential's rpId is fixed at creation, and the Signal API only deletes, hides, or renames credentials *within the same RP ID*. The options are: keep the old RP ID and reach it from new origins through Related Origin Requests, which needs a host you control at the old RP ID and works only where supported; or have users log in with the old passkey, enrol a new one under the new RP ID, and then use `signalAllAcceptedCredentials` or `signalUnknownCredential` to retire the old ones. The Signal API is in Chrome and Edge 132 and Safari 26, and not in Firefox.

**Cited Findings:**

- "A public key credential can only be used for authentication with the same entity (as identified by RP ID) it was registered with." — [WebAuthn L3 §4](https://www.w3.org/TR/webauthn-3/#rp-id)
- Signal methods check the RP ID with the same suffix rule, falling back to Related Origin Requests. "If rpId is a registrable domain suffix of or is equal to effectiveDomain, return a promise resolved with undefined. If the client does not support related origin requests, return a promise rejected with a 'SecurityError' DOMException." Otherwise the client runs the related origins validation procedure. — [WebAuthn L3 §5.1.10.1](https://www.w3.org/TR/webauthn-3/#sctn-signal-methods)
- `signalUnknownCredential` "signals that a credential id was not recognized by the WebAuthn Relying Party". The authenticator action removes or hides the credential only "If the credential's rpId equals options.rpId and the credential's id equals" the given ID. It is designed for unauthenticated callers. — [WebAuthn L3 §5.1.10.2](https://www.w3.org/TR/webauthn-3/#sctn-signal-methods)
- `signalAllAcceptedCredentials` "Signals the complete list of credential ids for a given user." RPs "SHOULD prefer this method ... when the user is authenticated". `signalCurrentUserDetails` "signals the user's current name and displayName." — [WebAuthn L3 §5.1.10.3–5.1.10.4](https://www.w3.org/TR/webauthn-3/#sctn-signal-methods)
- Spec note: "Signal methods intentionally avoid waiting for authenticators to complete executing the authenticator actions". — [WebAuthn L3 §5.1.10](https://www.w3.org/TR/webauthn-3/#sctn-signal-methods)
- Support: all three methods are Chrome 132, Edge mirror, Safari 26, Firefox false. — [MDN BCD PublicKeyCredential.json](https://github.com/mdn/browser-compat-data/blob/main/api/PublicKeyCredential.json). Chrome's doc lists Chrome 132 on desktop and Android. It says Google Password Manager reflects signals, and that extension-based providers on desktop "decide whether to reflect the signal". Calling `signalAllAcceptedCredentials` with valid passkeys left out hides them, and a later call restores them. Its text calls Safari "supportive but not yet implemented" while its badge says 26, so the page is internally inconsistent and dated Nov 2024. — [Chrome, Signal API](https://developer.chrome.com/docs/identity/webauthn-signal-api)
- Safari 26 bugs: WebKit bug 298951 reports the `signalAllAcceptedCredentials` promise never resolving — [WebKit Bugzilla 298951](https://bugs.webkit.org/show_bug.cgi?id=298951). A vendor claims (Aug 2026, unverified) that on iOS and macOS 26 the Signal API deleted passkeys of unrelated accounts, and advises calling `signalUnknownCredential`, never `signalAllAcceptedCredentials`, on failed logins — [Corbado blog](https://www.corbado.com/blog/signal-api-ios-passkey-deletion-bug.md).

**Inferences:**

- The Signal API cannot rename an RP ID or carry a passkey across. It is a cleanup tool for after re-enrolment, not a migration tool.
- A practical domain move: (1) Keep the old host serving and accepting login. (2) After a user logs in on the old RP ID, prompt them to create a passkey on the new domain. Conditional create (Chrome 136+, Safari 18+) can do this as an automatic upgrade on the new origin, provided the user has another logged-in session there. (3) On the old origin, call `signalAllAcceptedCredentials` with an empty or reduced list for migrated users. That must run on the old origin, or the new origin needs Related Origin Requests pointing at the old RP ID. (4) Fall back to email or another recovery path for users who never come back.
- For Tetsu, the cheapest course is to choose the final RP ID, Tetsu's own apex domain, before any real user enrols. Treat any passkeys on `tetsu-demo.onrender.com` as throwaway demo credentials.

**Gaps:**

- I found no source on whether iCloud Keychain, 1Password, Bitwarden, or Windows Hello act on Signal API calls, beyond Google Password Manager and the general note about Chrome extensions.
- I did not verify the WebKit bug 298951 fix status or the reported iOS 26 deletion bug against Apple sources.
